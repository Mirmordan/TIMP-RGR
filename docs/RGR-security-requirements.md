# РГР: требования к безопасности и доступу

## Ожидаемый результат

- Понятная предметная область и решаемая проблема ИБ.
- Роли пользователей и защищенный доступ.
- Журналирование действий.
- Обработка ошибок, документация, проверенные сценарии.
- Работа показывает не только код, но и назначение системы, угрозы и защиту данных.

## Обязательные механизмы

1. Аутентификация
   - вход по логину или email;
   - пароль проверяется сервером;
   - пароль хранится только в виде хеша;
   - проверка сложности пароля;
   - сообщение об ошибке без раскрытия причины;
   - после входа используется токен или сессия.

2. Авторизация
   - проверка роли пользователя;
   - разграничение доступных страниц;
   - разграничение разрешенных API-запросов;
   - запрет действий без прав;
   - запрет прямого доступа к чужим данным;
   - единый формат ошибок.

3. Роли
   - минимум 3 роли;
   - роли описывают разные возможности;
   - администратор управляет пользователями, ролями, правами доступа и журналом.

## Безопасность API

Для каждого эндпоинта в документации должно быть понятно:

- метод и путь;
- входные параметры;
- открытые и защищенные эндпоинты;
- роли/права, которым доступен запрос;
- как проверяется токен или сессия;
- какие действия логируются;
- код и формат ошибки при отказе доступа.

## Защита интерфейса

- Пользователь видит только доступные ему разделы.
- Опасные действия требуют подтверждения.
- Сообщения об ошибках не раскрывают лишние технические детали.
- Есть журнал действий.
- Есть разграничение прав по ролям.
- Раздел администратора доступен только администратору/уполномоченным ролям.

## Разделы макета

1. Страница авторизации.
2. Главная страница.
3. Рабочий раздел с таблицами, поиском, фильтрами и кнопками создания/изменения/удаления.
4. Карточка объекта с деталями, статусом, историей изменений и ответственным.
5. Раздел администратора: пользователи, роли, права доступа, журнал действий.

## Тестирование

Функциональные проверки:

- регистрация/вход/выход;
- создание, просмотр, изменение, удаление данных;
- поиск, фильтрация, сортировка;
- обработка ошибок.

Проверки безопасности:

- неверный пароль;
- доступ к закрытой странице без авторизации;
- API без токена;
- действие без нужной роли/права;
- некорректные данные;
- SQL-инъекции;
- XSS через поля ввода;
- хранение пароля в виде хеша.

## Документация и сопровождение

Документация должна включать:

- цель, предметную область, назначение;
- структуру БД;
- архитектуру;
- API;
- порядок запуска;
- настройки безопасности;
- тестовые сценарии и результаты.

Сопровождение:

- резервное копирование;
- порядок обновления;
- мониторинг и логи;
- восстановление после сбоя;
- масштабирование.

## Выводы для текущей задачи

Реализуемая система доступа должна:

1. Поддерживать наследуемые свойства у объекта: название и описание как атрибуты `objects`, от которых зависят устройства, потоки, записи и связанные инциденты.
2. Использовать ALC/ACL для объектных прав: доступ к конкретным камерам, потокам, записям и группам объектов.
3. Иметь отдельный слой специальных прав для действий вне классического объектного доступа: управление пользователями, ролями, правами, журналирование, redaction и т.п.
4. Предоставлять администратору удобный API/UI: выдавать объекты ролям по имени и ID, просматривать пользователей роли и объекты группы.
5. Проверять каждый сценарий: нет права -> 403, есть право -> 200, нет токена/роли -> соответствующий отказ, интерфейс не показывает недоступный раздел.
